# Production Control

Учебный backend для учёта производства на **Python / FastAPI**. В нём можно создать производственный участок, завести партию, добавить продукты и отметить их агрегацию — по одному или фоновой задачей.

Если вы впервые открыли проект, сначала пройдите запуск и пример ниже, затем прочитайте [руководство разработчика](docs/development.md). Оно объясняет слои, бизнес-правила, транзакции и порядок добавления новой функции.

## Что уже есть

| Возможность | Состояние в коде |
| --- | --- |
| Участки | Создание, чтение по ID, удаление; чтение с Redis-кешем |
| Партии | Создание, чтение, частичное обновление полей, фильтрация, удаление без продуктов и CSV-экспорт |
| Продукты | Создание, одиночная агрегация, массовая агрегация через Celery |
| Фоновые задачи | RabbitMQ принимает задачи; Redis хранит их результаты |
| Производственная сводка | SQL → DTO → XLSX → загрузка в MinIO реализованы в Python |
| HTTP API отчётов | Запуск через Celery, статус задачи, скачивание через временную ссылку MinIO |
| Автоматические тесты | 8 unit-тестов `WorkCenterService`; интеграционных тестов и тестов CSV-экспорта пока нет |

Состояние описано по исходникам на **13 сентября 2026 года**. Наличие реализации не означает, что весь сценарий прошёл интеграционную проверку. Frontend и авторизация в проекте отсутствуют.

## Запуск на своём компьютере

Нужны **Python 3.11**, **Poetry 2** и **Docker с Compose**. Python 3.11 — версия проверенного локального окружения; в `pyproject.toml` разрешён диапазон `>=3.11,<4.0`. Docker Desktop должен быть запущен. Команды выполняйте из корня репозитория — папки с `pyproject.toml`.

Проверьте установку инструментов:

```bash
python3 --version
poetry --version
docker compose version
```

### 1. Подготовьте Python и настройки

```bash
poetry env use python3.11
poetry install --no-root
```

`--no-root` устанавливает зависимости без упаковки самого проекта: приложение импортируется из `src` при запуске из корня репозитория.

Создайте `.env` из шаблона **только если файла ещё нет**:

```bash
if [ ! -f .env ]; then cp .env.example .env; fi
```

Значения в `.env.example` подходят для Python на компьютере и инфраструктуры в Docker. Уже настроенный `.env` сохраняйте. Описание переменных — в [руководстве](docs/development.md#настройки).

### 2. Запустите инфраструктуру

```bash
docker compose up -d
docker compose ps -a
```

Дождитесь `healthy` у PostgreSQL, RabbitMQ, Redis и MinIO. `minio-init` должен завершиться с `Exited (0)`: он создаёт buckets и настраивает автоматическое удаление старых файлов (импорт и CSV-экспорт через 7 дней, отчёты через 30 дней). Compose запускает **только инфраструктуру**, API и Celery нужно запустить отдельно.

### 3. Создайте таблицы

```bash
poetry run alembic upgrade head
poetry run alembic current
```

Текущая единственная миграция: `8031c80a68ab`. `upgrade head` применяет недостающие миграции; повторный запуск при актуальной схеме ничего не меняет.

### 4. Запустите API

В первом терминале:

```bash
poetry run uvicorn src.main:app --reload
```

Откройте [Swagger UI](http://127.0.0.1:8000/docs). Здесь можно раскрыть endpoint, нажать **Try it out**, заполнить JSON и нажать **Execute**.

```bash
curl -sS http://127.0.0.1:8000/health
```

Ожидается `{"status":"ok"}`. Этот маршрут проверяет только ответ API: он **не проверяет подключения** к БД, очереди и хранилищам.

### 5. Запустите обработчик фоновых задач

Во втором терминале, также из корня проекта:

```bash
poetry run celery -A src.tasks.celery_app:celery_app worker --loglevel=info --pool=solo
```

В третьем терминале запустите планировщик webhook-доставок:

```bash
poetry run celery -A src.tasks.celery_app:celery_app beat --loglevel=info
```

`solo` обрабатывает задачи последовательно и подходит для первого локального запуска. Без worker фоновые задачи остаются в очереди. Без Celery Beat webhook-доставки останутся в статусе `pending`.

## Первый сценарий через Swagger

Пример создаёт данные в вашей локальной БД. Записывайте ID из ответов: они могут отличаться от `1`. При повторном прохождении измените идентификатор участка, номер партии и коды продуктов, чтобы не получить конфликт уникальности.

**1. Создайте участок:** `POST /api/v1/work-centers`, ожидается `201`.

```json
{"identifier": "DEMO-WC-01", "name": "Учебный участок"}
```

**2. Создайте партию:** `POST /api/v1/batches`, ожидается `201`. Вместо `work_center_id: 1` подставьте ID участка из первого ответа.

```json
{
  "task_description": "Учебная партия",
  "work_center_id": 1,
  "shift": "Дневная",
  "team": "Бригада 1",
  "batch_number": 91001,
  "batch_date": "2026-09-10",
  "nomenclature": "Учебная деталь",
  "ekn_code": "DEMO-EKN-01",
  "shift_start": "2026-09-10T08:00:00+05:00",
  "shift_end": "2026-09-10T20:00:00+05:00"
}
```

Время должно содержать часовой пояс; конец смены должен быть позже начала.

**3. Добавьте продукт:** `POST /api/v1/products`, ожидается `201`. Подставьте реальный ID партии.

```json
{"unique_code": "DEMO-P-001", "batch_id": 1}
```

**4. Агрегируйте продукт:** `PATCH /api/v1/products/DEMO-P-001/aggregate`, без тела запроса. Ожидается `200`, `is_aggregated: true` и заполненное `aggregated_at`. В этом MVP агрегация означает установку отметки; упаковок и иерархии кодов пока нет.

**5. Проверьте очередь:** создайте второй продукт `DEMO-P-002` в той же партии, затем вызовите `POST /api/v1/products/aggregate-bulk`:

```json
{"unique_codes": ["DEMO-P-002", "DEMO-NOT-FOUND"]}
```

Ожидается `202` с `task_id`. Подставьте его в `GET /api/v1/products/tasks/{task_id}`. После обработки ожидается:

```json
{
  "task_id": "ID из ответа POST",
  "status": "SUCCESS",
  "result": {
    "processed": ["DEMO-P-002"],
    "failed": [{"unique_code": "DEMO-NOT-FOUND", "reason": "Текст ошибки о ненайденном продукте"}]
  }
}
```

Здесь `task_id` и `reason` — поясняющие заглушки. `SUCCESS` означает завершение функции worker: отдельные продукты всё равно могут находиться в `failed`.

**6. Проверьте бизнес-ограничение:** закройте партию через `PATCH /api/v1/batches/{batch_id}` с `{"is_closed": true}`. PATCH принимает любое подмножество изменяемых полей партии; явно передавать `null` нельзя. Попытка добавить продукт в закрытую партию должна вернуть `409`. Повторное открытие доступно тем же PATCH с `false`.

## Создание и скачивание отчёта

После первого сценария в БД уже есть партия. Убедитесь, что worker и MinIO запущены.

1. В Swagger вызовите `POST /api/v1/reports/production-summary` **без тела**. Ответ `202`: `{"task_id":"...","status":"queued"}`.
2. Скопируйте `task_id` в `GET /api/v1/reports/tasks/{task_id}`. Повторяйте запрос до `SUCCESS` или `FAILURE`.
3. При `SUCCESS` поле `result` содержит `report_id`, `bucket: "reports"` и `object_name: "production-summary/<report_id>.xlsx"`.
4. Откройте в браузере `http://127.0.0.1:8000/api/v1/reports/<report_id>/download`, заменив `<report_id>` на UUID из результата. API вернёт `307`, браузер перейдёт по временной ссылке MinIO и скачает XLSX.

**`task_id` — ID задачи Celery, `report_id` — ID созданного файла. Они различаются.** Ссылка действует 15 минут; для новой ссылки снова откройте маршрут скачивания. Для скачивания удобнее браузер или `curl -L`, поскольку Swagger может столкнуться с ограничениями браузера при переходе на другой origin.

```bash
# Замените UUID на report_id из SUCCESS. Выберите свободное имя файла.
report_id='00000000-0000-0000-0000-000000000000'
curl --fail --location "http://127.0.0.1:8000/api/v1/reports/${report_id}/download" --output production-summary.xlsx
```

В Excel ожидаются строки партий, включая закрытые и партии без продуктов. Если партий вообще нет, фоновая задача завершается `FAILURE`, а endpoint статуса возвращает `result: null`; причину смотрите в логах worker. Неизвестный корректный UUID при скачивании даёт `404`, неверный формат UUID — `422`, обработанная недоступность MinIO — `503`.

## Экспорт партий в CSV

CSV-экспорт использует те же фильтры, что и список партий, но выгружает все совпавшие записи без пагинации.

1. Вызовите `POST /api/v1/batches/export/csv`, при необходимости добавив query-параметры, например `?is_closed=false&shift=Дневная`.
2. Полученный `task_id` передавайте в `GET /api/v1/batches/export/tasks/{task_id}` до статуса `SUCCESS`.
3. Возьмите `report_id` из `result` и откройте `GET /api/v1/batches/exports/{report_id}/download`.
4. API вернёт `307` на временную ссылку MinIO; для `curl` используйте флаг `--location`.

CSV имеет разделитель `;`, кодировку UTF-8 с BOM и строку заголовков. Пустая выборка создаёт файл только с заголовками. Подробный разбор того, как эта фича проектировалась и собиралась по слоям, находится в [примере разработки фичи](docs/feature-development-example.md).

## Ежедневная работа

```bash
# Проверка стиля без изменения файлов
poetry run ruff check .

# Unit-тесты (без внешних сервисов, но с настройками из .env)
poetry run pytest -q

# Состояние миграций в БД
poetry run alembic current

# Логи инфраструктуры
docker compose logs --tail=100 postgres rabbitmq redis minio minio-init

# Остановка инфраструктуры с сохранением данных
docker compose stop

# Повторный запуск
docker compose up -d
```

API и worker останавливаются через `Ctrl+C` в соответствующих терминалах. Не добавляйте `-v` к `docker compose down` при обычной остановке: этот флаг удаляет volumes с данными.
