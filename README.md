# Production Control

Учебный backend для учёта производства на **Python / FastAPI**. Он управляет участками, партиями и продуктами, строит статистику, обрабатывает CSV- и Excel-файлы и отправляет webhook-уведомления.

Если вы впервые открыли проект, начните с инструкций по запуску и примеров ниже.

## Что уже есть

| Возможность | Состояние в коде |
| --- | --- |
| Участки | Создание, чтение по ID и удаление |
| Партии | CRUD, фильтры, статистика, сравнение, импорт и экспорт CSV/Excel |
| Продукты | Создание, одиночная и массовая агрегация |
| Аналитика | Сводка дашборда, статистика партии, сравнение партий |
| Отчёты | Фоновая генерация XLSX и скачивание через временную ссылку MinIO |
| Webhooks | Подписки, шесть типов событий, HMAC-подпись, повторные доставки и история попыток |
| Инфраструктура | PostgreSQL, RabbitMQ, Celery/Beat, Redis, MinIO и Flower |
| Тесты | Unit-тесты импорта, фильтров, кешей, участков и настройки MinIO; интеграционных тестов пока нет |

Наличие реализации не означает, что весь сценарий прошёл интеграционную проверку. Frontend и авторизация в проекте отсутствуют; настройки и пароли в `.env.example` предназначены только для локального запуска.

## Архитектура

HTTP-запрос проходит через **Router → Service → Unit of Work → Repository → PostgreSQL**. Service проверяет бизнес-правила; Redis ускоряет чтение, а после изменения данных кеш инвалидируется. Долгие операции API ставит в RabbitMQ: Celery worker обрабатывает задачу и сохраняет результат в Redis. Файлы импорта, экспорта и отчёты хранятся в MinIO. Celery Beat периодически запускает диспетчер webhook-доставок; Flower показывает состояние фоновых задач.

Beat ежедневно в 01:00 по `PRODUCTION_TIMEZONE` ставит задачу `batches.auto_close_expired`. Worker закрывает открытые партии с `shift_end` раньше времени начала запуска. Перед закрытием срок проверяется повторно под блокировкой строки. Каждая партия сохраняется отдельной транзакцией вместе с записью события `batch_closed`, затем её кэш инвалидируется. Повторный запуск пропускает закрытые, удалённые и продлённые партии. При временной ошибке подключения к БД задача повторяется до трёх раз; уже сохранённые закрытия сохраняются. Такой суточный график допускает задержку автозакрытия до следующего запуска.

Каждые пять минут Beat запускает `analytics.update_cached_statistics`: worker пересчитывает статистику существующих партий из PostgreSQL порциями по 200 и обновляет Redis. Также обновляются общий дашборд, сводка за текущую дату производства и расширенный дашборд аналитики. Остальные сочетания фильтров кешируются при запросах API. При сбое Redis фоновая задача повторяется до трёх раз, вместо сообщения об успешном обновлении. Обычные запросы чтения по-прежнему могут работать через БД при недоступном кеше. Сроки хранения файлов обслуживаются lifecycle-правилами MinIO, настроенными `minio-init`.

API, worker и Beat выводят логи в JSON через Loguru. Существующие сообщения стандартного `logging` тоже направляются в этот формат.

`GET /api/v1/batches/{id}` возвращает поля партии и список `products`: `id`, `unique_code`, `is_aggregated`, `aggregated_at`. Для партии без продукции список пуст. Детали кешируются вместе с продукцией; после создания или агрегации продукта кеш деталей партии сбрасывается, в том числе при фоновой агрегации.

## Статусы фоновых задач

Основной маршрут — `GET /api/v1/tasks/{task_id}`. Старые маршруты `/products/tasks/{task_id}`, `/reports/tasks/{task_id}`, `/batches/import/tasks/{task_id}` и `/batches/export/tasks/{task_id}` под префиксом `/api/v1` возвращают ту же структуру: `task_id`, `status`, `progress`, `result`, `error`. Они принимают ID любой задачи проекта; результат сохраняет исходные поля независимо от выбранного URL.

При `PROGRESS` заполнен `progress`, при `SUCCESS` — `result`, при `FAILURE` — `error`. Неизвестный или истёкший ID возвращает `PENDING`, поскольку Celery не отличает его от ещё не начавшейся задачи. Внутренние ошибки скрыты за сообщением `Task failed; check worker logs`; ошибки формата импорта и экспорта, а также отсутствие данных для сводки возвращают понятную причину.

## Ограничение частоты запросов

Для одного IP разрешено 60 запросов `POST`, `PUT`, `PATCH` и `DELETE` к `/api/v1/` за 60 секунд. Запуск импорта CSV/Excel, экспорта CSV/Excel, массовой агрегации и отчёта дополнительно ограничен общим лимитом 10 запусков за тот же период. Такие запросы учитываются в обоих лимитах. `GET`, проверка состояния сервиса и опрос статуса задач не ограничиваются.

Настройки: `RATE_LIMIT_ENABLED=true`, `RATE_LIMIT_WINDOW_SECONDS=60`, `RATE_LIMIT_WRITE_REQUESTS=60`, `RATE_LIMIT_BACKGROUND_REQUESTS=10`. Период каждого счётчика начинается с первого разрешённого запроса. При превышении API возвращает `429` с заголовком `Retry-After`; при недоступности Redis защищённые запросы получают `503`. Разрешённая попытка учитывается даже при последующей ошибке валидации. Изменения настроек требуют перезапуска API, изменения кода в Docker — пересборки образа API.

## Запуск через Docker Compose

Нужен Docker с Compose. Все команды выполняйте из корня репозитория. Создайте `.env` из шаблона **только если его ещё нет**:

```bash
if [ ! -f .env ]; then cp .env.example .env; fi
docker compose up -d --build
docker compose ps -a
```

Compose поднимает PostgreSQL, RabbitMQ, Redis, MinIO и Flower; контейнер `minio-init` создаёт buckets и настраивает сроки хранения файлов, `migrate` применяет Alembic-миграции. Только после их успешного завершения запускаются `api`, `worker` и `beat`. Одновременно запускайте только один Beat: он периодически ставит в очередь задачи отправки webhook.

Откройте [Swagger UI](http://127.0.0.1:8000/docs) и проверьте API:

```bash
curl -sS http://127.0.0.1:8000/health
```

Ожидается `{"status":"ok"}`. Этот маршрут проверяет ответ API, а не все внешние сервисы. Flower доступен по адресу `http://127.0.0.1:5555`; учётные данные задаёт `FLOWER_BASIC_AUTH` в `.env`. Если сервис не запустился, смотрите `docker compose ps -a` и `docker compose logs --tail=100 api worker beat migrate minio-init`.

В контейнерах используются имена сервисов `postgres`, `rabbitmq`, `redis`, `minio`, а временные ссылки на файлы указывают на `localhost:9000` для браузера на вашем компьютере. Не запускайте одновременно контейнеры `api`/`beat` и их локальные копии: API займёт тот же порт, а два Beat будут дублировать периодические задачи.

### Альтернатива: запуск Python локально

Нужны Python 3.11 и Poetry 2. Установите зависимости и поднимите только инфраструктуру:

```bash
poetry env use python3.11
poetry install --no-root
docker compose up -d postgres rabbitmq redis minio minio-init flower
poetry run alembic upgrade head
```

После этого в трёх отдельных терминалах из корня проекта запустите API, worker и Beat:

```bash
poetry run uvicorn src.main:app --reload
poetry run celery -A src.tasks.celery_app:celery_app worker --loglevel=info --pool=solo
poetry run celery -A src.tasks.celery_app:celery_app beat --loglevel=info
```

При локальном запуске адреса `localhost` из `.env.example` подходят без изменений. `--no-root` устанавливает зависимости без упаковки проекта: модуль `src` импортируется из корня репозитория. Worker с `--pool=solo` обрабатывает задачи по одной, что удобно для разработки.

## Первый сценарий через Swagger

Пример создаёт данные в вашей локальной БД. Записывайте ID из ответов: они могут отличаться от `1`. При повторном прохождении измените идентификатор участка, номер партии и коды продуктов, чтобы не получить конфликт уникальности.

**1. При необходимости создайте участок отдельно:** `POST /api/v1/work-centers`, ожидается `201`. При создании партии участок также может создаваться автоматически.

```json
{"identifier": "DEMO-WC-01", "name": "Учебный участок"}
```

**2. Создайте партии:** `POST /api/v1/batches`, ожидается `201`. Тело запроса — массив от 1 до 1000 элементов. Участок определяется по `ИдентификаторРЦ`: существующий используется без переименования, отсутствующий создаётся. Ответ — массив созданных партий; запишите `id` нужного элемента.

```json
[
  {
    "СтатусЗакрытия": false,
    "ПредставлениеЗаданияНаСмену": "Учебная партия",
    "РабочийЦентр": "Учебный участок",
    "ИдентификаторРЦ": "DEMO-WC-01",
    "Смена": "Дневная",
    "Бригада": "Бригада 1",
    "НомерПартии": 91001,
    "ДатаПартии": "2026-09-10",
    "Номенклатура": "Учебная деталь",
    "КодЕКН": "DEMO-EKN-01",
    "ДатаВремяНачалаСмены": "2026-09-10T08:00:00",
    "ДатаВремяОкончанияСмены": "2026-09-10T20:00:00"
  }
]
```

Время без пояса трактуется в `PRODUCTION_TIMEZONE` (по умолчанию `Asia/Yekaterinburg`), время с поясом сохраняет указанный момент. Внутри оба значения переводятся в UTC; конец смены должен быть позже начала. При ошибке любого элемента весь список откатывается. Повтор партии с теми же номером и датой возвращает `409`. Для входящей закрытой партии `closed_at` фиксирует время приёма.

Русские ключи соответствуют предоставленному примеру из ТЗ. Также принимаются английские имена полей из схемы `BatchIntegrationItem`.

**3. Добавьте продукт:** `POST /api/v1/products`, ожидается `201`. Подставьте реальный ID партии.

```json
{"unique_code": "DEMO-P-001", "batch_id": 1}
```

**4. Агрегируйте продукт:** `PATCH /api/v1/products/DEMO-P-001/aggregate`, без тела запроса. Ожидается `200`, `is_aggregated: true` и заполненное `aggregated_at`. В этом MVP агрегация означает установку отметки; упаковок и иерархии кодов пока нет.

**5. Проверьте очередь:** создайте второй продукт `DEMO-P-002` в той же партии, затем вызовите `POST /api/v1/products/aggregate-bulk`:

```json
{"unique_codes": ["DEMO-P-002", "DEMO-NOT-FOUND"]}
```

Ожидается `202` с `task_id`. Подставьте его в `GET /api/v1/products/tasks/{task_id}`. После обработки ожидается:

```json
{
  "task_id": "ID из ответа POST",
  "status": "SUCCESS",
  "result": {
    "processed": ["DEMO-P-002"],
    "failed": [{"unique_code": "DEMO-NOT-FOUND", "reason": "Текст ошибки о ненайденном продукте"}]
  }
}
```

Здесь `task_id` и `reason` — поясняющие заглушки. `SUCCESS` означает завершение функции worker: отдельные продукты всё равно могут находиться в `failed`.

**6. Проверьте бизнес-ограничение:** закройте партию через `PATCH /api/v1/batches/{batch_id}` с `{"is_closed": true}`. PATCH принимает любое подмножество изменяемых полей партии; явно передавать `null` нельзя. Попытка добавить продукт в закрытую партию должна вернуть `409`. Повторное открытие доступно тем же PATCH с `false`.

## Отчёт по партии: Excel, PDF и email

`POST /api/v1/batches/{batch_id}/reports` принимает `{"format": "excel"}` или `{"format": "pdf", "email": "person@example.com"}`. Формат по умолчанию — Excel; email необязателен. API проверяет партию и возвращает `202` с `task_id`. Запуск учитывается в общем лимите фоновых задач.

Читайте результат через `GET /api/v1/tasks/{task_id}`. При `SUCCESS` поле `result` содержит `report_id`, `batch_id`, `format`, `download_url`, `email_status` и `email_task_id`. Excel содержит три листа: сведения о партии, продукцию и статистику. PDF содержит сведения, показатели и график накопленного количества агрегаций по точному времени события. Время отображается в `PRODUCTION_TIMEZONE`; пустая партия тоже получает отчёт.

Файл хранится в bucket `reports` по пути `batches/{batch_id}/{report_id}.xlsx` или `.pdf`. `GET /api/v1/batches/{batch_id}/reports/{report_id}/download?format=excel` (или `pdf`) выдаёт перенаправление на ссылку MinIO, действующую 15 минут. В письме дана ссылка на API, поэтому при открытии создаётся новая ссылка MinIO. После удаления файла по сроку хранения скачивание возвращает 404.

Уведомление отправляется отдельной задачей: `email_status=queued` означает постановку в очередь, а не доставку. Проверьте её по `email_task_id` через общий статус задач; `SUCCESS` означает принятие письма SMTP-сервером. При ошибках SMTP отправка повторяется до трёх раз, без повторной генерации отчёта. При сбое постановки письма в очередь отчёт остаётся доступным, а `email_status=queue_failed`. Повторные попытки SMTP не гарантируют отсутствие дублирующих писем.

Для локального запуска Compose добавляет Mailpit: письма доступны на [localhost:8025](http://localhost:8025), наружу они не отправляются. По умолчанию контейнеры используют SMTP `mailpit:1025`. Для запуска Python вне Docker задайте `SMTP_HOST=localhost`. Для реальной отправки настройте `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURITY` (`starttls` или `ssl`), `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM_EMAIL` и доступный получателю `PUBLIC_API_URL`. Секреты храните в локальном `.env`.

## Создание и скачивание общей сводки

После первого сценария в БД уже есть партия. Убедитесь, что worker и MinIO запущены.

1. В Swagger вызовите `POST /api/v1/reports/production-summary` **без тела**. Ответ `202`: `{"task_id":"...","status":"queued"}`.
2. Скопируйте `task_id` в `GET /api/v1/reports/tasks/{task_id}`. Повторяйте запрос до `SUCCESS` или `FAILURE`.
3. При `SUCCESS` поле `result` содержит `report_id`, `bucket: "reports"` и `object_name: "production-summary/<report_id>.xlsx"`.
4. Откройте в браузере `http://127.0.0.1:8000/api/v1/reports/<report_id>/download`, заменив `<report_id>` на UUID из результата. API вернёт `307`, браузер перейдёт по временной ссылке MinIO и скачает XLSX.

**`task_id` — ID задачи Celery, `report_id` — ID созданного файла. Они различаются.** Ссылка действует 15 минут; для новой ссылки снова откройте маршрут скачивания. Для скачивания удобнее браузер или `curl -L`, поскольку Swagger может столкнуться с ограничениями браузера при переходе на другой origin.

```bash
# Замените UUID на report_id из SUCCESS. Выберите свободное имя файла.
report_id='00000000-0000-0000-0000-000000000000'
curl --fail --location "http://127.0.0.1:8000/api/v1/reports/${report_id}/download" --output production-summary.xlsx
```

В Excel ожидаются строки партий, включая закрытые и партии без продуктов. Если партий вообще нет, фоновая задача завершается `FAILURE`, а endpoint статуса возвращает `result: null`; причину смотрите в логах worker. Неизвестный корректный UUID при скачивании даёт `404`, неверный формат UUID — `422`, обработанная недоступность MinIO — `503`.

## Экспорт партий в CSV и Excel

`POST /api/v1/batches/export` выгружает все совпавшие партии без пагинации. Пример JSON:

```json
{
  "format": "excel",
  "filters": {
    "is_closed": false,
    "date_from": "2026-10-01",
    "date_to": "2026-10-02"
  }
}
```

1. Выберите `format`: `csv` или `excel`.
2. Полученный `task_id` передавайте в `GET /api/v1/tasks/{task_id}` до `SUCCESS` или `FAILURE`.
3. При `SUCCESS` откройте `result.download_url`. API возвращает `307` на временную ссылку MinIO; для `curl` используйте `--location`.

Фильтры соответствуют списку партий. `date_from` и `date_to` ограничивают `batch_date` включительно; можно указать только одну границу. Обратный диапазон и сочетание диапазона с точной `batch_date` дают `422`. Диапазон также доступен в query-параметрах списка партий.

CSV: разделитель `;`, UTF-8 с BOM. Excel: один лист «Партии» с теми же колонками. Если текст поля Excel превышает 32 767 символов, экспорт завершается `FAILURE` с понятной причиной в `GET /api/v1/tasks/{task_id}`; обрезанный файл не создаётся. Пустая выборка создаёт файл с заголовками. Файлы сохраняются в bucket `exports`; срок хранения задаёт `MINIO_EXPORT_RETENTION_DAYS`.

Старый `POST /api/v1/batches/export/csv` с query-фильтрами сохранён. Скачивание старых CSV из bucket `reports` поддерживается. Для ручного скачивания: `GET /api/v1/batches/exports/{report_id}/download?format=csv` или `format=excel`.

## Импорт партий из CSV и Excel

Сначала создайте участок: в файле нужен его существующий `work_center_id`. Загрузите `.csv` или `.xlsx` в поле `file` через `POST /api/v1/batches/import`.

Обязательные заголовки:

```text
task_description;work_center_id;shift;team;batch_number;batch_date;nomenclature;ekn_code;shift_start;shift_end
```

CSV должен быть в UTF-8 с разделителем `;`. Excel читается с первого листа, заголовки находятся в первой строке. Для дат подходят ISO-строки, для Excel также обычные ячейки дат. Время без часового пояса трактуется в `PRODUCTION_TIMEZONE` и переводится в UTC. Необязательная колонка `is_closed` сохраняет состояние партии; ID и служебные даты из экспорта не переносятся.

1. Ответ `202` содержит `task_id` и означает постановку в очередь.
2. Опрашивайте `GET /api/v1/tasks/{task_id}` до `SUCCESS` или `FAILURE`.
3. При `SUCCESS` смотрите `result.processed` (номер строки и ID партии) и `result.failed` (номер строки и причина ошибки).

Каждая корректная строка сохраняется отдельной транзакцией. Ошибки данных и ограничения БД пропускают конкретную строку, затем импорт продолжается. Сбой соединения или другая системная ошибка останавливает задачу; уже сохранённые строки остаются в БД. Повреждённый файл или неверные заголовки завершают задачу с `FAILURE`. Поэтому `SUCCESS` не означает отсутствие ошибок строк.

По умолчанию: файл до 5 МиБ, до 10 000 строк данных, распакованный Excel до 50 МиБ. Формулы Excel запрещены. Настройки: `BATCH_IMPORT_MAX_FILE_SIZE_BYTES`, `BATCH_IMPORT_MAX_ROWS`, `BATCH_IMPORT_MAX_UNCOMPRESSED_BYTES`.

Для импорта должны работать API, PostgreSQL, RabbitMQ, Redis, MinIO и Celery worker. Исходный файл остаётся в bucket `imports` до удаления по сроку хранения. Старый `/api/v1/batches/import/csv` сохранён как совместимый маршрут.

## Аналитика и webhooks

- `GET /api/v1/analytics/dashboard` — блоки `summary`, `today`, `by_shift`, `top_work_centers`, `cached_at`. Фильтры: `date_from`, `date_to` (включительно по `batch_date`), `work_center_id`, `shift`. Обратный диапазон даёт `422`.
- `GET /api/v1/batches/{batch_id}/statistics` — прежние счётчики плюс `batch_info`, `timeline`, `team_performance`, `cached_at`.
- `POST /api/v1/analytics/compare-batches` с JSON `{ "batch_ids": [1, 2] }` — сравнение 2–10 уникальных положительных int32 ID: `items`, `average`, `overall_products_per_hour`. Если хотя бы одна партия отсутствует, ответ `404` с её ID.
- Старые `GET /api/v1/dashboard/summary` и `GET /api/v1/batches/compare?batch_ids=1&batch_ids=2` сохранены с прежними ответами.

### Правила расчёта аналитики

`today` показывает состояние партий с сегодняшней `batch_date` в `PRODUCTION_TIMEZONE`, с учётом остальных фильтров. Если диапазон не включает сегодня, блок содержит нули. Это не число операций агрегации за календарный день. Партии без продуктов включаются в счётчики. Пять первых участков ранжируются по количеству агрегированных продуктов, при равенстве — по ID.

`duration_hours` — `(shift_end - shift_start)` в часах. `elapsed_hours` — время от начала смены до текущего момента, ограниченное концом смены и временем закрытия. В `timeline.products_per_hour` число агрегаций с `aggregated_at` внутри этого рабочего интервала делится на прошедшее время. Агрегации без времени или вне интервала учитываются в общих счётчиках, но не в текущем темпе.

Прогноз относится только к уже зарегистрированным продуктам: `now + (total_products - aggregated_products) / products_per_hour` часов. Плановое количество из текста задания не извлекается. `forecast_status` объясняет результат: `available`, `no_products`, `not_started`, `no_progress`, `batch_closed`, `shift_finished`, `completed`. При отсутствии обоснованного прогноза возвращается `estimated_completion_at: null`; при полном завершении — время последней агрегации, если оно известно. Текущий темп и прогноз пересчитываются при каждом запросе по кешированному снимку счётчиков.

`team_performance` относится к бригаде, указанной в партии; индивидуальная производительность сотрудников не рассчитывается. В сравнении `products_per_hour` означает агрегированные продукты на час **полной смены**, включая открытые партии с предварительными показателями. `average` — арифметическое среднее по партиям; `overall_products_per_hour` — сумма агрегированных продуктов, делённая на сумму длительностей. Проценты и темп округляются до двух знаков, длительности — до четырёх.

Кеш аналитики использует поколения существующих кешей: изменения партий и продуктов инвалидируют его после commit. Ключ дашборда включает локальную дату, поэтому переход суток меняет блок `today`. `cached_at` — время формирования сохранённого снимка, в UTC; на попаданиях в кеш не меняется. При недоступном Redis чтение продолжается из PostgreSQL с `cached_at: null`. Дашборд собирается одним SQL-запросом, сравнение читает все выбранные партии одним запросом.

TTL поколений вдвое больше TTL данных: участки и списки партий — 120 секунд, статистика и дашборд — 600, детали партии — 1200 по умолчанию. Чтение не продлевает TTL. После истечения создаётся новый случайный токен; запись результата старого запроса остаётся в старом поколении. Запрос к отсутствующей записи возвращает `404` без создания ключа. На первом чтении существующей записи создаётся поколение, а кеш заполняется следующим SQL-чтением, чтобы сохранить защиту от одновременных изменений.

После обновления API, worker и Beat один раз назначьте TTL ранее накопленным бессрочным ключам:

```bash
docker compose exec -T api python - < scripts/expire_cache_generations.py
```

Команда использует `SCAN` и `EXPIRE NX`: сохраняет токены, данные кеша и уже назначенные сроки жизни; повторный запуск безопасен.


### Webhooks

- `/api/v1/webhooks` — создание, просмотр, изменение и деактивация подписок. Список возвращает `{ "items": [...], "total": 123 }`, принимает `offset` и `limit` (1–100).
- `GET /api/v1/webhooks/{id}/deliveries` — история выбранной подписки с `items`, `total`, `offset` и `limit`. Несуществующая подписка даёт `404`, отсутствие доставок — пустой список.
- Старые `/api/v1/webhook-subscriptions` и `/api/v1/webhook-deliveries` сохранены; их ответы имеют прежний формат.

Новое тело уведомления содержит `event_id`, `event`, `timestamp` (UTC, ISO 8601) и `data`. В `batch_updated` поле `data.changes` содержит только реальные изменения: `{ "shift": { "old": "Day", "new": "Night" } }`. В `batch_closed` добавляется `data.statistics`: `batch_id`, `total_products`, `aggregated_products`, `pending_products`, `aggregation_percent`. Это снимок из БД в момент ручного или автоматического закрытия. Повторное сохранение тех же значений не создаёт событие.

Изменение партии и записи доставок сохраняются одним commit: откат отменяет оба. Тело уведомления фиксируется до отправки; повторы используют те же байты и `event_id`. Получатель должен распознавать повторные события по `event_id`. Ранее созданные доставки сохраняют прежнее тело с `event_type` и `occurred_at`.

Подписка выбирает события из `batch_created`, `batch_updated`, `batch_closed`, `batch_reopened`, `product_created`, `product_aggregated`, `report_generated`, `import_completed`. После события запись о доставке сохраняется в PostgreSQL. Celery Beat периодически запускает диспетчер, worker отправляет HTTP-запрос с HMAC-подписью и при необходимости повторяет попытку. Секрет подписки нужно заранее передать принимающему сервису по защищённому каналу. Адреса вебхуков ограничены публичными HTTP/HTTPS-назначениями; авторизация API остаётся отдельной задачей.

`report_generated` создаётся после сохранения отчёта по партии (Excel/PDF) или общей сводки в MinIO. В `data` передаются `task_id`, `report_id`, `report_type`, `format`, `download_url`; для отчёта по партии также `batch_id`. `import_completed` создаётся после завершения CSV/Excel-импорта, в том числе частично успешного: `data` содержит `task_id`, `format`, `total`, `imported`, `failed`, `batch_ids`, `errors` с номером строки и причиной. При общей ошибке генерации, загрузки или импорта событие завершения не создаётся. Записи доставок сохраняются через commit до возврата результата задачи; их отправка выполняется существующим диспетчером.

При отправке DNS проверяется один раз. Если подключение к первому IP не удалось, клиент пробует следующий проверенный IP; исходные `Host` и TLS SNI сохраняются. На подключения и HTTP-запрос действует общий таймаут подписки (DNS проверяется отдельно, до 5 секунд), а время подключения делится между адресами. Ошибки записи/чтения и полученный HTTP-ответ не запускают переход к следующему IP: POST уже мог быть доставлен. Запланированные повторы доставки обрабатываются отдельно по `retry_count`.

## Ежедневная работа

После локальной установки зависимостей через Poetry:

```bash
# Проверка стиля без изменения файлов
poetry run ruff check .
poetry run ruff format --check .
poetry run mypy
poetry run bandit -q -r src scripts

# Unit-тесты (без внешних сервисов, но с настройками из .env)
poetry run pytest -q

# Все проверки разом; после установки зависимостей можно также выполнить
# poetry run pre-commit install, чтобы запускать их перед каждым коммитом.
poetry run pre-commit run --all-files
```

Для запуска через Compose:

```bash
# Состояние миграций в БД
docker compose exec api alembic current

# Логи приложения и инфраструктуры
docker compose logs --tail=100 api worker beat migrate postgres rabbitmq redis minio minio-init

# Остановка всех контейнеров с сохранением данных
docker compose stop

# Повторный запуск
docker compose up -d
```

При локальном запуске API, worker и Beat останавливаются через `Ctrl+C` в соответствующих терминалах. Не добавляйте `-v` к `docker compose down` при обычной остановке: этот флаг удаляет volumes с данными.


### Ограничения вебхуков и массовой агрегации

Массовая агрегация принимает от 1 до 1000 уникальных кодов. Подписка вебхука принимает поле `timeout` (1–60 секунд, по умолчанию 10); старое имя `timeout_seconds` также принимается на вход, в ответе используется `timeout`.

При создании и обновлении подписки URL проверяется на публичный адрес. Приватные, loopback, link-local, multicast и зарезервированные диапазоны IPv4/IPv6 отклоняются с `422`; DNS не должен возвращать ни одного запрещённого адреса. Worker повторяет проверку каждой доставки, включая ранее сохранённые URL, и подключается к проверенному IP с исходными Host и TLS SNI. Redirect и proxy из окружения отключены. При блокировке доставка получает запись об ошибке; локальные получатели в Docker запрещены.

Экспорты хранятся в bucket `exports` с префиксом `batch-exports/` и сроком хранения 7 дней по умолчанию (`MINIO_EXPORT_RETENTION_DAYS`). Старые файлы экспорта в `reports` сохраняют прежнее правило очистки. Пустая производственная сводка возвращает `FAILURE` с `error: "No production data available for report"`.
